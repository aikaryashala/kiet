Compilation & execution · one stage per page

From sum.c to a running process

One command hides six separate programs. --save-temps tells clang to keep every intermediate file it would normally throw away, so you can open each one and see exactly what changed. Walk the stages in order — each page shows one file, the tool that produced it, and what is inside it.

$ clang --save-temps sum.c -o sum
Leaves sum.i, sum.ll, sum.s, sum.o and sum sitting in your directory.
Stage 01 · Source · you wrote this

The file the machine cannot run

sum.c

What sum.c containsHuman-readable C text: directives that have not been acted on yet, a macro name that stands for a number, comments for people, and two functions that no CPU understands.

sum.c
#include <stdio.h>

#define N 5

/* add up 1..n the slow, obvious way */
int sum(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++)
        total += i;
    return total;
}

int main(void) {
    printf("sum = %d\n", sum(N));
    return 0;
}

Three things to notice

  • #include and #define are not C statements — they are instructions to a separate program that runs first.
  • printf is used here but not defined anywhere in this file.
  • The comment is for you. It will not survive the next stage.

Predict before you click

Which of the three things above disappears at stage 2? Which one survives all the way to stage 6 as an unfilled hole?

Stage 02 · Preprocessing

Paste, substitute, strip

sum.c→ clang -E→ sum.i

What sum.i containsPure C with every #include file pasted in whole, every macro replaced by its value, and every comment deleted — one flat translation unit of roughly 800 lines.

Exactly what changed

  • #include <stdio.h> became ~800 lines of declarations — promises about functions, no code.
  • sum(N) became sum(5). The name N no longer exists.
  • The comment is gone.
  • Lines like # 3 "sum.c" are bookkeeping so error messages can still point at your original line numbers.

Try it yourself

wc -l sum.c sum.i — two files, same program, wildly different line counts. That gap is the preprocessor.

The point

Nothing was compiled yet. This stage is pure text surgery — copy, replace, delete.

Stage 03 · Front end → intermediate representation

One language for every machine

sum.i→ clang -S -emit-llvm→ sum.ll

What sum.ll containsLLVM IR — a typed, machine-independent instruction language where your loop has become explicit blocks and branches, and which every optimizer pass reads and rewrites.

sum.ll  (abridged)
; ModuleID = 'sum.c'
source_filename = "sum.c"
target triple = "x86_64-pc-linux-gnu"

@.str = private unnamed_addr constant [10 x i8] c"sum = %d\0A\00", align 1

define i32 @sum(i32 noundef %n) {
entry:
  %n.addr = alloca i32, align 4
  %total  = alloca i32, align 4
  %i      = alloca i32, align 4
  store i32 %n, ptr %n.addr, align 4
  store i32 0, ptr %total, align 4
  store i32 1, ptr %i, align 4
  br label %for.cond

for.cond:
  %0 = load i32, ptr %i, align 4
  %1 = load i32, ptr %n.addr, align 4
  %cmp = icmp sle i32 %0, %1
  br i1 %cmp, label %for.body, label %for.end

for.body:
  %2 = load i32, ptr %i, align 4
  %3 = load i32, ptr %total, align 4
  %add = add nsw i32 %3, %2
  store i32 %add, ptr %total, align 4
  %4 = load i32, ptr %i, align 4
  %inc = add nsw i32 %4, 1
  store i32 %inc, ptr %i, align 4
  br label %for.cond

for.end:
  %5 = load i32, ptr %total, align 4
  ret i32 %5
}

define i32 @main() {
entry:
  %call  = call i32 @sum(i32 noundef 5)
  %call1 = call i32 (ptr, ...) @printf(ptr noundef @.str, i32 noundef %call)
  ret i32 0
}

declare i32 @printf(ptr noundef, ...)

Exactly what changed

  • The 800 lines of declarations vanished — only printf, the one you actually called, survives as a declare.
  • Your for loop is gone. In its place: four labelled blocks and br jumps between them.
  • The string literal moved out of main into a named global, @.str.
  • Types are still everywhere: i32, ptr, [10 x i8].

Why bother with an IR?

Every optimisation is written once against IR instead of once per CPU. Add a new language front end or a new chip back end, and everything in the middle still works.

No registers yet

%0, %total, %add are unlimited virtual registers, not real hardware ones. Picking real registers is the next stage's job.

Stage 04 · Back end → code generation

Real registers, real stack offsets

sum.ll→ llc  (clang -S)→ sum.s

What sum.s containsx86-64 assembly text — actual CPU instructions using actual register names and byte offsets from the frame pointer, still readable by a human but tied to one processor family.

sum.s
        .text
        .globl  sum
sum:
        pushq   %rbp                # save caller's frame pointer
        movq    %rsp, %rbp
        movl    %edi, -4(%rbp)      # n
        movl    $0, -8(%rbp)        # total = 0
        movl    $1, -12(%rbp)       # i = 1
.LBB0_1:
        movl    -12(%rbp), %eax
        cmpl    -4(%rbp), %eax      # i <= n ?
        jg      .LBB0_4
        movl    -12(%rbp), %eax
        addl    %eax, -8(%rbp)      # total += i
        addl    $1, -12(%rbp)       # i++
        jmp     .LBB0_1
.LBB0_4:
        movl    -8(%rbp), %eax      # return value in %eax
        popq    %rbp
        retq

        .globl  main
main:
        pushq   %rbp
        movq    %rsp, %rbp
        subq    $16, %rsp
        movl    $5, %edi            # 1st argument = 5
        callq   sum
        movl    %eax, %esi          # 2nd printf argument
        leaq    .L.str(%rip), %rdi  # 1st printf argument
        movb    $0, %al
        callq   printf
        xorl    %eax, %eax          # return 0
        addq    $16, %rsp
        popq    %rbp
        retq

        .section .rodata.str1.1,"aMS",@progbits,1
.L.str:
        .asciz  "sum = %d\n"

Exactly what changed

  • Virtual registers became real ones: %eax, %edi, %esi.
  • Local variables became offsets: total is now -8(%rbp).
  • The calling convention appeared — arguments go in %edi, %esi; return values come back in %eax.
  • .globl marks sum and main as visible to other files.

Still just text

You can open sum.s in any editor and edit it by hand. Nothing here is binary yet.

Change one flag

Compile with -O2 and this file shrinks dramatically — the optimiser can compute sum(5) at compile time and the loop disappears entirely.

Stage 05 · Assembling

Text becomes bytes

sum.s→ as  (clang -c)→ sum.o

What sum.o containsA relocatable ELF object file: real machine-code bytes for sum and main, plus a symbol table where printf is still marked undefined and its address left as a hole.

0000000000000031 T main

Exactly what changed

  • Each instruction now has its encoding: push %rbp is the single byte 55.
  • Both call targets are e8 00 00 00 00 — zeros. The address is not known yet.
  • Every zero-hole is recorded as a relocation (R_X86_64_PLT32): a note saying "linker, patch this spot with the address of printf".
  • nm says it plainly — T = defined here, U = undefined, someone else must supply it.

Why "relocatable"?

Addresses start at 0 because this code does not yet know where in the final program it will sit. The linker decides that and shifts everything accordingly.

Not runnable

Try ./sum.o — permission denied. It has code, but no entry point and no resolved addresses.

Stage 06 · Linking

Filling in every hole

sum.o libc.so→ ld  (the linker)→ sum

What sum containsA complete ELF executable: your object code combined with C startup code, every relocation patched, printf resolved against libc.so.6, and a recorded entry point for the operating system.

file sum  ·  ldd sum  ·  nm sum
$ file sum
sum: ELF 64-bit LSB executable, x86-64, dynamically linked,
     interpreter /lib64/ld-linux-x86-64.so.2, not stripped

$ ldd sum
     linux-vdso.so.1
     libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
     /lib64/ld-linux-x86-64.so.2

$ nm sum | grep -E ' (main|sum)$|printf'
0000000000001149 T main
                 U printf@GLIBC_2.2.5
0000000000001139 T sum

$ readelf -h sum | grep Entry
  Entry point address:     0x1040        <- _start, not main

$ ls -l sum
-rwxr-xr-x  1 rohini  16696  sum          <- x = executable

What the linker did

  • Gave every function a final address — sum at 0x1139, main at 0x1149.
  • Went back to each relocation hole and wrote the real number in.
  • Added the C runtime startup object (crt1.o) which defines _start — the true entry point.
  • Recorded a dependency on libc.so.6 instead of copying printf's code in.

Static vs dynamic

Dynamic linking keeps sum at ~16 KB and lets every program on the machine share one copy of libc in memory. clang -static sum.c copies libc in instead — the file jumps to megabytes.

Still one loose end

printf is resolved to a name, not yet to an address. The final address is bound when the program is loaded — which is the next page.

Stage 07 · Loading · ./sum

From disk into memory

sum  (on disk)→ loader→ code + data in RAM

What the loader does firstIt copies the code section (your instruction bytes) and the data section (globals and the string "sum = %d\n") out of the file and into RAM at fixed addresses.

What comes from the file

SectionHolds
.textMachine code for sum, main, startup
.rodataThe string "sum = %d\n" — read-only
.dataInitialised globals
.bssZeroed globals — takes no space in the file, only in RAM

libc arrives too

The interpreter ld-linux.so runs first, loads libc.so.6 into the same memory space, and finally binds printf to a real address.

Simplified here: real systems do not copy the whole file in. They map virtual pages that the kernel fetches from disk only when first touched. "Copied into RAM" is the right mental model to start with; page tables come later.
Stage 08 · Loading · memory layout

Room to grow: stack and heap

code + data→ + stack & heap segments→ process image

What gets set up nextTwo regions that were never in the file: a stack at the high end that grows downward for function frames, and a heap just above the data that grows upward whenever you call malloc.

Stack

  • Holds one frame per active function call — parameters, locals, return address.
  • In sum, total and i live here at -8(%rbp) and -12(%rbp).
  • Managed automatically: push on call, pop on return. Nothing to free.

Heap

  • Only grows when you ask — malloc, calloc.
  • Lives until you free it, not until the function returns.
  • sum.c never touches it, so this region stays empty for our program.

They grow toward each other

That gap in the middle is shared. Runaway recursion eats it from the top; runaway allocation eats it from the bottom. Meeting in the middle is a stack overflow.

Stage 09 · Handing control to the CPU

Setting the program counter

process image→ PC ← address of main→ ready to execute

The final setup stepThe CPU's program counter is loaded with the address of main's first instruction — 0x1149 — and from that moment the hardware, not the loader, decides what happens next.

What the PC is

A single register inside the CPU holding the address of the next instruction to fetch. Every instruction executed bumps it forward; every jmp, call and ret overwrites it. That register is the whole of "where the program is right now".

The fetch–decode–execute loop

  • Fetch the bytes at the address in PC.
  • Decode them into an operation.
  • Execute it, and advance the PC.
  • Repeat, forever, until the process exits.
Simplified here: the PC is really set to _start in libc first. That code sets up argc, argv and the environment, then calls main for you. We jump straight to main because that is the part you wrote.
Stage 10 · Execution

Frames pushed, frames popped

fetch → decode → execute

What happens nowThe CPU walks the instructions one at a time, pushing a stack frame each time a function is called and popping it on return, until main reaches its own ret.

    The number that gets out

    main returns 0→ exit()→ exit status

    The last thing the process doesThe value main returns is handed to the exit system call, the kernel tears down the whole memory image, and the shell keeps that one number as the exit status.

    the whole thing, end to end
    $ clang --save-temps sum.c -o sum

$ ls
sum   sum.c   sum.i   sum.ll   sum.o   sum.s

$ ./sum
sum = 15

$ echo $?
0

$ ./sum ; echo "exit status was $?"
sum = 15
exit status was 0

    What "exit status" is for

    • 0 means success. Anything else means a failure the caller can act on.
    • It is the only value a program returns to whoever started it — everything else went to stdout.
    • Shell scripts branch on it: ./sum && echo ok only prints ok when the status is 0.
    • Only the low 8 bits survive, so return 256 arrives as 0.

    The whole journey

    One text file → one flat text file → typed IR → assembly text → machine-code bytes with holes → a patched executable → a memory image with a stack and a heap → a CPU walking instructions → the single number 0.

    Take it further

    Change return 0 to return 3, recompile, and watch echo $? change. Then diff sum.s before and after — one instruction moved.
